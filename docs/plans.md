# team.gg 구현 계획

## 현재 스프린트: 참가자 관계 숫자 키 전환

목표는 참가자 계열 테이블의 긴 문자열 PK·FK·보조 인덱스를 숫자 키로 바꿔 디스크와 I/O를 줄이는 것이다. 숙련도 테이블에서 같은 전환으로 약 25GB가 5GB로 줄었다. 세부 설계는 [numeric-key-schema-v2](plans/numeric-key-schema-v2.md)를 따른다.

1. **#70 참가자 숫자 키 백필**: 기존 `match_participants` 행의 participant PK·match FK·summoner FK를 백엔드 무중단으로 채우고 전체 정합성을 검증한다.
2. **#71 하위 관계 백필**: 스탯·밴·팀·`summoner_matches` 등 하위 테이블의 숫자 FK를 채운다. 룬 테이블은 제외한다.
3. **#72 숫자 관계 읽기 전환**: 필수 숫자 인덱스·FK를 적용하고 API·DataExplorer·통계를 숫자 JOIN으로 전환한다.
4. **#65 룬 평탄화**: 룬 테이블을 숫자 참가자 키 기반 참가자당 한 행 구조로 옮긴다.
5. **#75 legacy 문자열 키 제거**: 중복 문자열 FK·인덱스·호환 trigger를 단계적으로 제거하고 디스크 효과를 측정한다.

각 운영 실행은 retention 창(KST 02:00~04:00 시작, 최대 2시간)과 겹치지 않게 하고, 실행 전에 처리량·binlog·디스크 증가량을 추정한다.

## 미확정 선택지

- **패치별 파티셔닝**: 경기 계열 테이블을 패치 단위로 파티셔닝하면 retention이 행 DELETE 대신 `DROP PARTITION`으로 즉시 디스크를 반환할 수 있다. 숫자 키 전환 완료 후 검토한다.
- **DB 메모리**: InnoDB buffer pool을 384MiB로 늘렸지만 서버 RAM 3.8GiB에서 swap 약 2GiB를 이미 사용 중이다. 같은 MySQL을 다른 프로젝트(`mips`)도 쓰므로 인스턴스 확장 또는 메모리 재배분을 별도로 판단한다.
- **관리자 기능 확장**: 관리 기능이 쓰기 작업과 다중 운영자 승인 흐름까지 확대되면 독립 관리자 프론트엔드 분리를 재검토한다.
- **로그 수집**: 원문 애플리케이션 로그 검색이 필요해지면 Docker 소켓 마운트 대신 Loki/OpenSearch 같은 전용 로그 수집기를 도입한다.
- **역할 관리 UI**: 역할 부여·회수 UI는 감사 및 재인증 정책이 확정된 뒤 별도 task로 구현한다.
