## 목적

운영 디스크 증가를 통제하고, 사용 중인 데이터와 정리 가능한 데이터를 구분해 안전한 hot/archive/delete 정책을 구현한다.

## 현재 용량

| 시점 | 사용률 | 여유 공간 | 비고 |
|---|---:|---:|---|
| 조사 시작 | 95% | 약 7.7GiB | 즉시 정리 필요 |
| BuildKit·binlog 정리 후 | 79% | 약 27.2GiB | 비동기 GC 포함 |
| 숙련도 shadow 전환 후 | 85% | 약 20GiB | legacy와 numeric 동시 보관 |

## 완료된 조치

| 조치 | 결과 |

## 보존 후보

| 후보 | 예상 효과 | 선행 조건 |
|---|---:|---|
| legacy `masteries` | 약 20~25GiB OS 공간 | #73 직접 쓰기, 백업·rollback 검증 후 #74 |
| 8개 패치 이전 경기 | 약 1.5~2GiB 내부 공간 | S3 archive, manifest·checksum, 보존 기간 확정 |
| 30일 이상 비연동 소환사 | 약 2~3GiB 내부 공간 추정 | lazy refresh와 보호 관계 검증 |
| DataExplorer 완료 job | 수십 MiB 수준 | bounded cleanup 활성화 |
| migration legacy backup | 약 304MiB | rollback 보존 종료 승인 |

`DELETE`만으로는 InnoDB `.ibd`가 줄지 않을 수 있다. OS 공간 반환은 table/partition drop 또는 충분한 여유를 확보한 rebuild가 필요하다.

## 안전 기준

- archive 검증 전 원본을 삭제하지 않는다.
- 사용자 계정·내전 구성·리플레이 결과 연결 데이터는 자동 삭제하지 않는다.
- 여유 공간 12GiB 미만, lock wait, API 장애 발생 시 중단한다.
- `DROP`, `TRUNCATE`, 대형 rebuild는 별도 사용자 승인 후 실행한다.
