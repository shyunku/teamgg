# team.gg 작업 보드

`backend`, `frontend`, `replay` 세 앱의 미완료 작업을 관리합니다. 완료된 작업은 [tasks_done.md](tasks_done.md)에서 관리합니다.

## 관리 규칙

- 새 작업은 `🔴 TODO`로 등록하고, 실제 구현을 시작하기 직전에 `🟡 WIP`로 변경합니다.
- `🟣 VFY`는 작업자가 할 수 있는 일은 끝났고 사용자의 확인·판단·결정만 남은 상태입니다. 필요한 확인·결정 항목을 subtask 문서에 명시합니다. `VFY` 중 수정이 다시 필요하면 `🟡 WIP`로 되돌립니다.
- 작업자가 직접 할 수 있는 검증(테스트, 운영 데이터 조회, 정합성 확인, 장기 관측 등)은 일반 작업처럼 `TODO`/`WIP`/`DONE`으로 관리하며, 이런 검증이 남아 있으면 작업은 `WIP` 또는 `TODO`입니다. 검증 주체가 애매하면 사용자에게 묻습니다.
- 완료 조건을 모두 충족하고 가능한 범위의 빌드·테스트·검증을 마친 작업만 `🟢 DONE`으로 변경하고, 그 행을 `tasks_done.md`로 옮깁니다. 이 문서에는 DONE이 아닌 작업만 남깁니다.
- 동시에 실제 코드 구현 묶음 하나만 `WIP`로 두되, 배포·운영 규모 검증 대기 항목은 병행할 수 있습니다.
- `Tag`는 `backend`, `frontend`, `replay`, `unclassified` 중 하나만 사용합니다.
- `Updated`는 마지막 업데이트 일시, `Completed`는 완료 일시를 KST `YYYY-MM-DD HH:mm`으로 기록합니다. 기존 이력에 시각이 없으면 날짜만, 날짜가 없으면 `Updated`는 `—`로 두고 `Completed`는 비워 둡니다.
- 가장 큰 Index가 위에 오도록 정렬하며, 새 작업은 두 문서를 통틀어 현재 최댓값에 1을 더합니다. 삭제된 번호는 재사용하지 않습니다.
- `Deps`에는 반드시 먼저 완료되어야 하는 작업을 `#41, #5` 형식으로 기록하고, 없으면 비워 둡니다.
- `항목`에는 목적·작업 내용을 간결하게, `완료 조건`에는 완료를 판단할 수 있는 구체적인 조건을 기록합니다. 진행 결과와 판단은 상세 문서에 남깁니다.
- 세부 작업(subtask) 문서는 `docs/tasks/{3자리 Index}.md`로 만들고 Index 숫자에 링크합니다. 미완료 작업은 subtask 문서를 둡니다.
- subtask 문서는 제목과 목적 한두 문장, `## 세부 작업` 표(`Index | Updated | Status | Completed | Deps | 항목 | 완료 조건`, Index는 `70.1` 형식), `## 기록`(결과 지표·주요 결정·진행 기록) 순서로 작성합니다. 상태 값·일시·정렬 규칙은 이 문서와 같고, 모든 세부 작업이 DONE이어야 상위 작업을 DONE으로 바꿉니다. 긴 로그와 시행착오 전체는 `docs/reports/`로 분리합니다.
- `추천 작업 순서`에는 미완료 작업 중 다음에 진행할 작업을 의존성·운영 위험도·효과 기준으로 최대 20개까지 나열하고, 작업 추가 및 상태·의존성 변경 시 함께 갱신합니다. `tasks_done.md`와 subtask 문서에는 두지 않습니다.
